## Windows 左右 Shift 證據與適配

限定 READY。`windows-actors-v2` 的正常雙打記錄證實：兩人同按拳腳時為 `[48,48]`，第一人放開左 Shift 後，第二人尚按右 Shift 卻變成 `[0,16]`。固定 Ebitengine 2.9.9 的 `internal/glfw/win32_window_windows.go` 在 `_WM_KEYUP` 且 `_VK_SHIFT` 時明確呼叫兩鍵的 Release；此為來源事實，不推論 Windows 實體鍵盤一定同樣失敗。

獨立只讀探針 `tools/windows_shift_probe.go` 在同一 Wine 工具鏈、相同原生視窗焦點，以 `GetAsyncKeyState` 的 bit 15 取得 VK_LSHIFT=0xA0、VK_RSHIFT=0xA1。`workplace/windows-shift-v1/receipt.json` 證實未按、雙按、只放左鍵、再放右鍵依序為 `[false,false]`、`[true,true]`、`[false,true]`、`[false,false]`。不寫入遊戲或作業系統按鍵狀態。

- Windows 對戰按鍵僅將左右 Shift 的持續狀態改由這兩個明確 VK 讀取，其他鍵仍由 Ebitengine 提供。Linux 與 macOS 不改取值方式。
- 讀取只發生在既有焦點、設定、暫停與重新啟用檢查內。失焦仍釋放兩人來源；恢復時仍要求先放開按鍵。鍵盤與手把最後來源放開規則不變。
- 不改 DOS 掃描碼、快捷、傷害或設定格式。Win32 僅取 bit 15，不使用代表「自上次呼叫後曾按下」的 bit 0。
- 實作後重跑兩人同按與獨立放開的正常原生流程；Wine 證據仍不取代 Windows 真機。

研究用 `-observe` 可附上前端更新序號、左滑鼠鍵持續狀態及目前編輯角色。這些是只讀前端狀態，不進設定檔或原版記憶體。GUI 驅動逐次等待按下／放開各被前端取樣，再送下一次操作，不以固定短暫等待假設每個事件都已處理。正常玩家不需開啟此輸出。

## 60 fps 流暢度目標

使用者於 2026-10-21 明確選擇「保留原版動作節奏，目標穩定 60 fps 輸出」，並要求先在實際硬體確認根因，再修改時序。這是驗收目標，不能以設定值或影片檔標頭宣稱通過。

- 前端與輸入目標 60 Hz，畫面輸出目標 60 fps，每格預算約 16.67 ms。原版完成畫格另用 gamecore.Presentation.Serial 計算，不能把螢幕重繪、角色換姿態、原版對戰輪詢與影片格數混成同一個 FPS。
- 保留原版規則與動作節奏，不為湊畫格數修改 PIT、快捷蓄力、碰撞、傷害、倒數或音訊速度。HD 移動插值與補幀尚未授權。
- 量測同一二進位與同一正常選角／移動／跳躍／拳腳序列，分原貌、HD、錄影開關。記錄 renderer、CPU／GPU、資源限制、版本與雜湊、時間窗、實際前端更新／繪圖／原版畫格、步進與繪圖耗時。另列平均、p95、p99、最大值及超過 33.3 ms 的停頓，保留原始事件。
- 虛擬顯示的 NVIDIA EGL 實跑只能證明該 GPU 與容器路徑，不能代替實體螢幕掃描、輸入到光子的延遲或 Windows／macOS 真機。CPU 軟體繪圖、GPU 執行與錄影後轉檔分開，擷取條件必須寫入影片來源紀錄。
- 推廣片採 60 fps 原生擷取並核對實際畫面時間；重複上一格不算新的原版動作，後製加速或補幀不能代替遊戲效能驗收。既有 30 fps v1 影片保持，不覆寫歷史交付。

基準入口為 [原生效能量測](../../tools/native_perf.py)與本輪 workplace/flow-study-v1，實測結果及判定回填 CONTEXT／WORKLOG。本段先固定定義，60 fps 完成聲明須有正式程式與相同 GPU 條件的實際收據。

### 已審查的呈現優化與擷取節奏

限定 READY。ada 同一診斷版在 NVIDIA EGL 擷取路徑，VSync 開啟約 52 fps；關閉後約 189 fps，前端仍為 60 Hz、原版完成畫格約 24 Hz。固定 60 fps 節奏原型在二十秒邊錄影測試約 60.00 fps、1,202 個間隔平均 16.6665 ms、p99 26.33 ms、最大 31.67 ms，超過 33.3 ms 為零。這是擷取路徑的直接證據，不推論所有實體螢幕都要關閉 VSync。

- 新增可選 CLI `-capture-fps 60`，只接受 0 或 60；0 保留螢幕 VSync。擷取模式關閉 VSync，由呈現層的單調時鐘維持每秒六十次繪圖。錯過期限不積累無限補畫工作，過載重設下一個期限；不改 core.Step 預算、原版計時器或輸入規則。前端明確設定 60 TPS。
- HD 對戰快取只重用相同已完成畫格。鍵包含 Serial、Steps、HD 模式與 Victory 快照身分；勝負字圖可能在相同 Serial 晉升，不能僅比較 Serial。離開對戰、模式改變、來源更新即失效，F12 證據擷取強制重新合成。標題、選角及結果沿原來源辨識，不使用此快取。
- 原型在核心暫停時，經同一 X11 擷取路徑比較快取關閉與開啟，960×600、2,304,000 RGBA bytes 完全相等，core.Status 不變。正式版不加入原型的 F7 快取切換、環境開關或強制 CPU profiler。
- `-observe` 追加唯讀性能欄位：前端 FPS／TPS、步進／更新／繪圖耗時、繪圖次數、快取次數與最近六十四個畫格間隔。既有設定格式與原版資料不變；正常啟動未開觀測時不收集時間窗。
- 正式接入後以同樣 NVIDIA 路徑重測，並錄三名魔王選角及遊玩。原始圖像、核心與時鐘不變，舊 Release／影片保持。Windows／macOS 真機及實體螢幕延遲仍另驗。

### 正式擷取路徑驗證

限定 CONFORMED，範圍為 ada NVIDIA EGL 原生 Linux 與同時錄影。正式 `v.1.0.1-20261021` 二進位 SHA-256 `02390b1b0b6d7f00b49809f8c295462241567e36a146b0b5f29f07ed28a9b952`，正常雙打選角、移動與拳腳二十秒測得 60.0173856 fps／TPS，原版完成畫格 23.56756 fps。1,202 個繪圖間隔平均 16.6669868 ms、p95 19.082045 ms、p99 24.845035 ms、最大 30.633105 ms，超過 33.3 ms 為零；CPU 配額節流為零，對手實際扣血。完整事件及 renderer 證據在 workplace/flow-study-v1/ada-results/ada-formal-60。

收據的 vsync=on 是診斷環境請求；正式程式不讀該環境變數，命令列 capture_fps=60 才是實際模式，會關閉 VSync。原型快取／重新合成的 960×600 RGBA 完全相同，核心狀態不變，證據在同根的快取比較收據。沒有把原型 F7、CPU profiler、PIT 調整或 PGO 帶進正式版。二十秒取樣不能宣稱所有長流程、實體螢幕、原版動作六十新格或其他平台已通過。
