## 輸入與證據

工具為 IDA Pro 9.4、Go 1.24.13、固定 1715 檔 dosgolem 副本及獨立 Python 重組。位址保留 runtime `01B9:IP`、DS 相對偏移與 IDA MZ 線性位址，不將它們當作同一個數值。

| 原檔 | SHA-256 |

| SF.EXE | `24b23d41c5fe6015d211b601e44b4e030677363f7232adcf9999c9ddd80d8300` |
| BOARD.XBB | `a1b789d9187f77c70b28a5dfe782af258f6a84c6260ac4b20e55817e0c00b7ff` |
| NAME.XBB | `60c0bbe367e44ab9fda512df2ba93ad62d70147df90079d07ff15818f21bad82` |

- IDA 原名 `sub_13284` 的 runtime 32EFh 起讀 BOARD.XBB 前 2800h bytes 到背景段加 1000h 的 8000h；3332h 起讀 0-9.XBB 前 834h bytes 到 DS:2F28h。SF.EXE 的 DS:2F12h 十個原始 word 依序為 `0,210,...,1890`，資料段原檔基底 A610h，三種位址基準另列。
- `sub_133F4` 讀取 NAME.XBB，以角色編號索引開頭的 word 指標，目的地為原介面左側 9A52h、右側 9B6Eh 減原圖寬。圖像 header 為 width、height，後接 8-bit 色號；每列目的步幅 320。`sub_13667` 的原指令證實此格式。
- `sub_115C7` 設 DS:169Ch／169Eh 為 7Ch，DS:2F26h 為 64h。`sub_13FEC` 消費 DS:16A0h／16A2h 的待扣傷害，每次更新最多兩格，並由 `sub_1409B`／`sub_140BD` 修改介面像素。呈現讀顯示生命值，不改用生命減待扣傷害。
- `sub_13F29` 在 DS:1Ah 低三位為 7 時減少 DS:2F26h，以 AAM 拆十位／個位，從 0-9.XBB 各複製 14×15 到介面 `(145,9)`、`(161,9)`。此值是原版顯示數字，不另換算成秒。
- `sub_13FAA` 把上述 320×32 bitmap 的非零像素 OR A0h，寫到 DS:000Eh 合成段，目的起點為 DS:1334h 乘 320。3FEBh 為恢復 DS 後的 RET。BOARD.COL 實檔 768 bytes；原版只讀前 96 bytes 到 A0h 起的 32 色，本介面使用其中前 16 色。
- 勝場欄位為 DS:131Eh／1320h。圖示在 `sub_133F4` 建立介面時才更新。134E6h 的 RET 可鎖存該次顯示勝場數；它與回合結束時已更新的規則數值可能不同。必須分開保存，不能讓 HD 提前顯示新圖示。

上述為已證實的取樣範圍。`hud-draw-v3` 正常標題、雙打、雙方普通移動與拳擊，取得 1176 次介面繪製，像素及等值寫入覆蓋均吻合；走到第一次擊倒及第二回合。33 個保存 fixture 可由五份原檔、欄位及顯示勝場鎖存獨立重組。`hud-draw-v2` 未鎖存勝場的舊 fixture `hud-0973` 差 93 點，保留為舊推論被新證據否定的紀錄。

## 正式實作契約

- 以只讀快照保存 `Health[2]`、`Pending[2]`、`Timer`、`Characters[2]`、規則勝場、顯示勝場、回合及 bitmap。134E6h 鎖存顯示勝場，3FAAh 取得與此次實際繪製一致的其他欄位。原貌／HD 切換不能改寫其中任何值。
- 從固定來源重建期望 bitmap，逐點比對低四位並檢查透明性。接受 0..15 與原版逐格扣血／補血留下的 ADh／AEh；未知 bytes、欄位、色盤、指標或來源整格回退。
- 生命有效範圍 0..124，計時 0..99，角色 0..10，勝場 0..2，回合 0..8。若未觀察到 setup 或此次 HUD 完成點，不用其他畫格的資料猜補。動態收據涵蓋偏移 7..12；合成邊界仍按原版 320×200 檢查。
- 原六層／特效層順序不變。HUD 開始前保存最後原貌層，替換時移除此次已核對的原介面寫入，還原原介面之前的遮擋，再繪製高解析介面。不能以抹除固定矩形或背景蓋片代替來源與覆蓋觀測。
- 左生命條外框邏輯矩形為 `(18,12)..(143,20)`，內部為 `(19,13)..(143,19)`；右側為 `(177,12)..(302,20)`、`(177,13)..(301,19)`。左側扣血從外側向右，右側從外側向左。HD 以原顯示生命除 124 決定剩餘長度。
- 計時安全矩形為 `(145,9)..(175,24)`；斬名字為 `(18,21)..(60,32)`，法蘭克為 `(248,21)..(302,32)`。玩家標記從 BOARD.XBB 的非零像素取得邊界，第一人為 `(4,12)..(17,20)`，第二人為 `(303,12)..(320,20)`。不能遺漏第二人最右兩列。使用目前內嵌字型，量實際字寬及行高，縮放到安全矩形內，保留描邊空間，不靠裁切遮住溢出。
- 本輪高解析名字只替換已有完整來源群組的斬與法蘭克。勝場圖示與其他訊息維持原圖層，本切片的完成不能外推全部介面或其他角色完成。

## 驗收

`workplace/hud-evidence-review.json` 核對原檔、1176 次動態覆蓋、33 個獨立來源及寫入位置重組、勝場鎖存與第二回合後先升 READY。實作再通過 33 個真實介面與 19 個特效 fixture、來源損壞拒絕、全套測試與靜態分析。`hud-core-compat-v1` 的 456 個邊界在開／關觀測時原貌與狀態相同，取得 448 個完整介面快照。

正常 GUI 收據為 `native-hud-frank-v2`、`windows-hud-v1`、`windows-hud-frank-v1`，各十六項及十六張完整畫格重組通過。兩平台法蘭克案例驗實際扣血；三次暫停的原貌／HD 來源狀態與恢復後 HD 畫面相同。`native-hud-legacy-v1` 十三項及缺件整張原貌核對通過。四個二進位的實際編譯來源及上述項目由 `native-hud-audit.json` 核對，依此限定升 CONFORMED。

首版玩家二標記遺漏最右兩列，已用 BOARD.XBB fixture 重現，改由原檔非零邊界取得完整安全矩形，並要求前十二列之後的非零介面像素全部納入替換。首版擷取漏複製 `.hud-under.idx` 屬驗證工具問題，修正後正常流程乾淨重跑；不補造舊擷取。Wine 收據仍不能代替 Windows 真機、macOS 或實體手把。
